# Core

## Registry
`Registry` maps networked objects to NIDs; an RPC reaches an object only where it is registered under the same NID.
- `RegisterGameObject(ref baseID, go)` registers the root under `baseID`, then numbers the components under it positionally (`GetComponentsInChildren`, inactive ones included, skipping `MeshRenderer` and `MeshFilter`, and `SpriteSM` (`Graphics/`) and `Collider` on objects with more than 250 components). The component layout must match on every client or RPCs land on the wrong component.
- An object made by `AddComponent` or plain `Object.Instantiate` is registered only if its own type registers itself; otherwise RPCs addressed to it are dropped. An RPC passing it as an argument gets `null` in its place when its type is one `TypeSerializer` (`Net/`) caches; a class a mod declares never is, and that RPC fails outright. Register it with `RegisterObject(ref nid, obj)` or `RegisterGameObject` under the same NID on every client: allocate with `AllocateDeterministicID()` in the same order everywhere, or allocate once with `AllocatePlayerUniqueID()` and send the NID in an RPC. Registration returns false when the NID or the object is already registered.
- `AllocateDeterministicID` takes the next value of a per-machine counter that each level's `Registry` resets (`Awake` → `RegisterDeterministicObjects` → `Reset` → `ResetIDs`), so a deterministic ID matches across machines only when every machine allocates in the same order. Nothing refuses a deterministic registration made after the level's load-time pass: `allDeterministicObjectsHaveBeenRegistered` is set and never read.
- `Map.PlaceDoodad` (`Level/`) registers each doodad it places, doors included, with `RegisterDeterminsiticGameObject`, numbering the components the doodad has at that moment; a component added afterwards is not among them.
